# 切换策略设计：性价比模式与性能模式

> 状态：已采纳（P1 与 P2 的「UI 提示行显示模式」实现于本仓库；其余 P2/P3 待定）
> 范围：`llm-fallback` 插件的候选模型选择层

## 一、背景与问题

插件原本只有一种选型策略：链式惰性遍历 + 四种平局偏好（`closest` / `price` / `speed` / `reasoning`）。用户需要两种显式的切换模式：

1. **性价比模式（cost）**：切换时，在能支撑当前任务完成的前提下，选择价格最低的候选；
2. **性能模式（performance）**：切换时，在仍有额度的候选中，选择能力最强的模型。

两者共享同一个不可妥协的前提：**候选必须能支撑当前任务完成**——尤其对性价比模式，绝不能单纯按价格选择。

## 二、现状解剖（实现本设计前）

选型层是三层结构：**硬过滤 → 分组 → 平局偏好**。审读代码发现三个关键事实：

1. **`price` 偏好不是真价格。** `compareCandidates` 的 `price` 分支按 `contextWindow` 升序排序（"窗口小≈便宜"的代理）；真正的价格数据（`quota.prices`）只参与额度预警的成本估算，从不参与选型，且只支持 provider 级键——同 provider 下不同模型价格可差 10~100 倍。
2. **能力地板是"相对主模型"，不是"任务绝对需求"。** 原容量不降级以主模型的 `contextWindow` 为基准。会话已进行到 20k tokens、主模型窗口 128k 时，64k 窗口的候选会被误判为"降级"而排除——尽管它完全能支撑当前任务。**地板必须是动态的、绝对的。**
3. **可复用的估算机器已经存在。** `estimateInputTokens(session)` 实时估算当前上下文 token 量；`estimateCost()` 按价格投影单次请求成本；`belowThreshold` / `banUntil` / `healthyRoute` / 两阶段探测构成完整的可用性语义。双模式不是从零造轮子，而是把这些机器从"预警专用"提升为"选型通用"。

## 三、核心框架：地板 → 评分 → 确定性破平

两种模式共享同一决策架构，差异只在中间的评分函数：

```
候选全集（链全局展开）
  ┌─────────────────────────────────────────────┐
  │ 第一层：任务支撑地板（硬约束，两模式共享）          │
  │  F1 模态覆盖          （沿用现有）              │
  │  F2 上下文容量：window ≥ 当前用量 + marginTokens │
  │     （动态绝对地板，取代相对主模型的分组）          │
  │  F4 可用性：未 ban；披露额度 ≥ 本次请求投影成本     │
  │  F5 推理连续性        （P2）                   │
  ├─────────────────────────────────────────────┤
  │ 第二层：模式评分（软目标）                        │
  │  cost         → 期望成本 × 风险乘数，取最小        │
  │  performance  → 能力词典序（带显著性阈值），取最强   │
  ├─────────────────────────────────────────────┤
  │ 第三层：确定性破平：链位置 → id 字典序              │
  └─────────────────────────────────────────────┘
```

**核心原则：地板保证"能完成任务"，评分只决定"在能完成的前提下选谁"。** 价格永远只能在通过地板的候选之间起作用——这是"不能简单用价格选"的形式化。

## 四、"能支撑当前任务完成"的严格定义

### F2 动态上下文容量

```
floor = estimateInputTokens(session) + marginTokens
候选合格 ⟺ candidate.contextWindow ≥ floor
```

- `marginTokens` 默认 8192（含本步输出预留），可配置；
- 会话越长，合格候选自然越少——45k 会话时 32k 窗口的便宜模型无论多便宜都被排除；
- 窗口未知的候选：默认排除（策略路径要求可验证），`allowUnknownCapacity: true` 时保留并排在最后；
- 旧 `allowDegrade` 语义保留在 closest 路径；策略路径中地板无人满足即无候选（让真实失败接管）。

### F3 工具支撑（P2）

目录信号（`LlmResolvedModelInfo`）没有工具调用支撑标志。P2 方案：配置声明不支持工具的模型面板 + `unusableCodes` 试错自愈兜底（后者已有）。

### F5 推理连续性（P2）

失败路由带 `reasoningEffort` 时：性能模式 `strict`（排除非推理候选，默认）、性价比模式 `prefer`（风险乘数惩罚）。

## 五、性价比模式：期望成本 ≠ 单价

真正的性价比是 `总成本 / 任务完成概率`，两者都无法精确预知。设计上诚实：用可测量的主导项 + 会话内学到的风险项：

```
score(c) = expectedCost(c) × risk(c)

expectedCost = (inputTokens × inputPrice + estimatedOutputTokens × outputPrice) / 1e6 × futureSteps
               （续传场景重发全部上下文，输入价主导）

risk(c) = ∏ 已知风险因子：
  × sessionFailurePenalty   本会话该路由失败过（再失败的隐性成本）
  × cliffPenalty            窗口贴地板（余量 < marginTokens/2，上下文增长即被迫再切）
```

设计决策：

- **单步成本而非多步模拟**：未来步数不可知，多步期望是伪精确；`futureSteps` 仅作可选放大系数（默认 1）；
- **会话内失败惩罚**：风险项的唯一可学习来源——便宜货失败过一次，真实成本就要乘上再失败概率；
- **价格两级回退**：`prices['provider/model']` → `prices['provider']` → 无价（无法评分，排最后，破平走链位置→id）。

## 六、性能模式：把偏序变全序

"能力最强"的困难在于能力是偏序（A 窗口大、B 会推理）。加权评分权重任意、不可解释；纯词典序会被离群值劫持（1M 窗口的笨模型压过 256k 的推理模型）。

**采用带显著性的词典序**：

```
axes 默认 [reasoning, context, output]（轴序可配置）
每轴：显著差才分胜负（context/output 用比值 ≥ significantRatio，默认 1.5；reasoning 严格偏序）
轴内不分胜负 → 下一轴；全部平 → 链位置 → id 字典序
```

消除了噪声驱动的名次翻转，保证确定性（同一候选集永远同一结果——可测试、可在事件里解释），又避免离群值劫持。

## 七、架构决策：模式作用于全局展开

原链遍历是惰性、逐条的。模式若只作用于"单 provider 目录内选模型"，会出现链[0] 的最便宜模型比链[1] 的贵——违背"全局性价比最高"语义。

双模式走统一的全局展开结构：

```
mode = closest            → 保持现状：惰性链遍历（全部既有行为不变）
mode = cost/performance   → 全局展开所有链候选 → 地板过滤 → 模式评分 → 全局最优
                              破平：链位置（用户链序作为先验）→ id
```

链序从"硬遍历顺序"降级为"破平先验"。派发顺序：策略路径（mode ≠ closest）→ 规则路径（closest）。（历史注：早期版本曾有一层可插拔 `decisionProvider`，因无真实消费者已删除。）

**兼容性**：`preference` 保留原语义（closest 路径的平局偏好）；`strategy.mode` 是策略路径的唯一开关，二者独立，既有配置与测试不受影响。

## 八、升级阶梯：任务完成优先于模式偏好

```
性价比模式在同一步内连续 afterFailures 次（默认 2）失败后，
该步的选择临时升级为性能模式重新遍历。
```

这是"能完成任务"前提的运行时兜底：没有它，性价比模式最坏情况是"便宜→失败→次便宜→失败→…"的连锁浪费。计数是步内的（`StepState`），新步自然归零。

## 九、与现有机制的耦合

| 现有机制 | 双模式下的语义 |
|---|---|
| `healthyRoute` 会话粘性 | 不变；模式只在切换时起作用 |
| 两阶段探测 | 探测顺序 = 模式排名顺序（天然一致） |
| 预警切换 | 走同一选择路径，自动继承模式 |
| 升级阶梯 | 步内 cost→performance（见上） |
| 事件 | `llm/fallback` 增加 `mode`、`score`；`llm/quota-warning` 增加 `mode` |

## 十、数据缺口

| 信号 | 现状 | 方案 |
|---|---|---|
| per-model 价格 | provider 级 | 键支持 `provider/model`，两级回退（P1） |
| 工具支撑 | 无目录信号 | 配置声明 + 试错自愈（P2） |
| 当前上下文用量 | 已有 | 直接作为地板输入（P1） |
| 剩余额度 | 已有 | 披露时接入地板 F4（P1） |
| 生成速度 | 插件不包 stream | 从会话事件统计 tokens/sec EWMA（P3） |

## 十一、配置形态

```yaml
strategy:
  mode: cost | performance | closest
  floor:
    marginTokens: 8192
  cost:
    futureSteps: 1
    sessionFailurePenalty: 2.0
    cliffPenalty: 1.5
  performance:
    axes: [reasoning, context, output]
    significantRatio: 1.5
  escalation:
    afterFailures: 2
```

## 十二、边界推演

- 会话 45k，最便宜模型 32k 窗 → 地板排除 → 选 64k 的次便宜 ✓（不简单用价格）
- 工具循环中途切到不支持工具的模型 → P2 之前由 `unusableCodes` 试错自愈推进 ✓
- 性能模式下强模型全部 ban → 全局展开自然跳过，选次强 ✓
- 无价候选 → 无法评分 → 排最后，事件不携带 score ✓
- 唯一可用路由额度不足 → F4 选型期即排除；全排除则返回 undefined，让真实失败接管 ✓
- 全部候选贴地板 → cliff 惩罚是软信号，不排除（硬排除会自断后路）✓
